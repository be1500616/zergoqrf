# Proposal: Migrations and Conventions

**Status:** parked. Not active. Will be promoted to an active OpenSpec change when the team is adding the second or third real schema change after `fix-broken-database-connection` lands.

## Why

`fix-broken-database-connection` makes the 24 existing migrations runnable. It does not, however, enforce that the next 24 are written consistently. Today the migrations directory has:

- 24 hand-written SQL files, two filename formats (`0001_init.sql` and the `<UTC-timestamp>_<scope>_<verb>.sql` series).
- No `down.sql` discipline, no RLS-in-same-file rule, no convention document, no lint script, no pre-commit check.
- No RLS posture gate: a tenant table added without `enable row level security` ships silently.
- No fresh-apply test: when migrations never run, drift is invisible until production.
- No Tier A vs Tier B split: every test that touches the DB runs in the default `pytest` invocation, so CI fails on any developer machine without a DB.

This change is the second thing we do after the broken-connection fix. It enforces five rules with a small lint script, adds a 30-line RLS posture check, and writes the migrations README. It does not introduce `app_jobs`, `app_cache`, a snapshot fixture, or a fresh-apply replay test — those belong to `app-jobs-and-realtime-fanout` or to a later change when there is a real second migration to regress on.

## What Changes

- Adopt a single migration management approach: **raw SQL files under `infra/supabase/migrations/`, applied by the Supabase CLI** (`supabase db push` / `supabase migration up`). No Alembic, no ORM-managed DDL, no snapshot dumps. The SQL files already in the tree are the right format; they need a runner, conventions, and a guardrail.
- Enforce strict migration conventions (filename format, idempotency, additive-first for breaking changes, paired `down.sql` where it matters, separation from `seeds/`) via a pre-commit check and a `make lint-sql` job. New migrations that violate the convention fail CI.
- Add an RLS posture check that runs in CI: every table in the tenant-scope list must have `rowsecurity = true` and at least one policy. The check is a 30-line script, not a full OpenSpec spec.
- Add a `local-supabase-dev-loop` capability so the local dev loop is documented in OpenSpec: `make dev` (from `fix-broken-database-connection`) plus a small extension that also runs the lint and the RLS check.

## Non-Goals

- No `app_jobs`, no `app_cache`, no queue worker. Those belong to `app-jobs-and-realtime-fanout`.
- No fresh-apply snapshot test, no idempotency replay test, no `_zergo_migrations` shim table. Add when the second real migration is added and we have something to regress on.
- No CI workflow `migrations` job that blocks the build. `make lint-sql` and the RLS posture check are local-run by default; CI integration is a separate, smaller change.
- No Alembic, no Prisma, no Drizzle. The Supabase CLI is the runner.
- No replacement of the 24 existing migrations. We rename the legacy one and add a README; we do not rewrite history.
- No `Base.metadata.create_all` removal. That belongs to the promotion of this change, when we know whether the test paths rely on it.

## Capabilities

### New Capabilities

- `schema-and-migration-management`: one canonical source of truth for schema (raw SQL files in `infra/supabase/migrations/`), one runner (Supabase CLI), one set of conventions (filename, idempotency, additive-first, `down.sql` discipline, seeds split), and one set of guardrails (pre-commit, `make lint-sql`, RLS posture check).
- `multi-tenant-rls-posture`: standard RLS policy patterns, tenant-isolation test fixtures, and a release-gate check that blocks deploy if RLS is disabled on a tenant table.
- `local-supabase-dev-loop`: the `make dev` workflow from `fix-broken-database-connection` extended with `make lint-sql` and `make rls-check`, documented in `infra/supabase/README.md`.

### Modified Capabilities

- None. All three capabilities are new in this change.

## Impact

- `infra/supabase/config.toml`: pin the Supabase CLI project config (project name, ports, ignored schemas). Generated by `supabase init` if absent; checked in.
- `infra/supabase/migrations/`: rename the legacy `0001_init.sql` to `20250101000000_init_legacy.sql` so the timestamp rule applies uniformly.
- `infra/supabase/migrations/README.md` (new): filename convention, idempotency rule, additive-first rule, `down.sql` discipline, seeds split, no-`select-*`-in-policies.
- `infra/supabase/README.md` (new): documents the local loop, migration order, pooler vs direct, and the SLOs that would trigger a future broker.
- `scripts/lint_sql.sh` (new): runs the SQL lint checks (see `schema-and-migration-management` spec) and exits non-zero on any violation.
- `scripts/check_rls.py` (new): 30-line script that opens a service-role connection, lists `public` tables in the tenant-scope list, asserts `rowsecurity = true` and `pg_policies` non-empty for each. Exits non-zero on any failure.
- `.pre-commit-config.yaml`: add a local hook that runs `scripts/lint_sql.sh --staged` on changed `.sql` files.
- `Makefile` (root): add `lint-sql` and `rls-check` targets.
- `tests/test_rls_tenant_isolation.py` (new, Tier A — `make rls-check` is the Tier B counterpart): pure-Python checks of the script's logic, no DB required.
- `tests/fixtures/rls_tenant_scope.json` (new): the canonical tenant-scope table list, shared between the script and the test.

## Success Criteria

- All migrations follow the filename convention `<UTC-timestamp>_<scope>_<verb>.sql`; the legacy `0001_init.sql` is renamed in the same PR.
- `make lint-sql` is green on the existing 24 migrations (after the rename).
- `scripts/check_rls.py` is green on a fresh `supabase start` and on a cloud dev project.
- The RLS posture check fails the build if a tenant-scoped table is added without `enable row level security` and a `tenant_id` policy.
- `pre-commit run --all-files` runs the SQL lint on changed `.sql` files and blocks the commit on a violation.
- No SQLAlchemy `create_all` or ORM-managed DDL is reachable in production code paths. (The removal itself happens in a follow-up; this change adds the lint that catches new DDL.)

## Dependencies

- **Hard dependency** on `fix-broken-database-connection`. The lint script and the RLS posture check both need a working `Settings.database_url` and a runnable local Postgres.
- **Soft dependency** on the profile contract from `add-dev-prod-supabase-workflow`. The lint script and the RLS posture check both run against the `local` profile's DB; the same env-isolation contract applies.
- **Soft dependency** on `app-jobs-and-realtime-fanout`. When that change lands, its `app_jobs` and `app_cache` tables must be added to the tenant-scope list (locked to `service_role`) and the RLS posture check must allow them.
- **Blocks** `app-jobs-and-realtime-fanout`. The promoted version of that change adds `app_jobs` + `app_cache` migrations; those migrations are subject to the lint and the RLS posture check established here.

## Out of Scope (Parked Draft)

- `parked/app-jobs-and-realtime-fanout`: the `app_jobs` and `app_cache` tables, the worker, the cache helpers, the outbox pattern, and the SLOs. Lands when a feature in the tree actually needs async work or short-lived cache, in the same PR as the caller.

## Why Parked, Not Done Now

Ponytail: don't enforce rules before the activity exists. The first migration after `fix-broken-database-connection` will be added by a developer who reads `infra/supabase/migrations/README.md` (created in the promotion commit). Until then, the conventions are not load-bearing and the diff to add them later is one PR.

The RLS posture check is the exception: it could be added today, since the 24 existing migrations already need it. It is parked here because the script depends on a working `Settings.database_url` (from `fix-broken-database-connection`) and on a stable tenant-scope list. Both are available the moment `fix-broken-database-connection` lands, so the check can move to its own small change if the team prefers.

## Why Split From `fix-broken-database-connection`

`fix-broken-database-connection` is the broken-thing fix. This draft is conventions. Different diff, different reviewer, different "is it done" signal. The two should not be in one OpenSpec change because they have nothing to verify against each other.
